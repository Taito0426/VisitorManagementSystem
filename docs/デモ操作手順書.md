# 来館者記録管理システム デモ操作手順書

本書は詳細設計書（版数2.7）19章「デモシステム仕様」に基づく、営業提案・デモンストレーション用の手順です。

> **デモ版は商用構成（Entry / Standard / Professional）とは別の設定プロファイルです。**
> そのままの構成で商用提供しないでください（設計書 19.5節）。

## 1. 事前準備（デモ実施前に1回だけ）

### ① SQL Server Express のセットアップ

通常のオンプレ版と同一の手順です（導入手順書 2章①②）。デモ専用の追加作業はありません。
LocalDB のような無インストール実行はできません。

```
sqlcmd -S .\SQLEXPRESS -E -I -i db\00_CreateDatabase_SqlExpress.sql
sqlcmd -S .\SQLEXPRESS -E -I -i db\02_CreateLogin_SqlExpress.sql -v SvcPassword="<パスワード>"
```

`00_CreateDatabase_SqlExpress.sql` は本番用 `VisitorMgmt` とデモ用 `VisitorMgmtDemo` の
両方を作成します。**デモ用DBのスキーマ作成は不要です**（アプリが初回起動時に自動作成します）。

### ② appsettings.json のデモ設定

```json
{
  "Database": {
    "Provider": "SqlExpress"
  },
  "Demo": {
    "Enabled": true,
    "ConnectionString": "Server=.\\SQLEXPRESS;Database=VisitorMgmtDemo;User Id=svc_visitor;Password=***;TrustServerCertificate=True;Encrypt=False;",
    "SeedOnFirstRun": true,
    "AllowResetFromAdminMenu": true
  },
  "Printing": {
    "Provider": "PdfPreview"
  }
}
```

**ポイント**
- `Database:Provider` は `"SqlExpress"` のまま変更しません。接続先のみ `Demo:ConnectionString` に切り替わります
- `Printing:Provider` を `"PdfPreview"` にすると、感熱式ラベルプリンタの代わりに A4 PDF で
  ラベルレイアウトと送信メール文面を確認できます（上半分＝ラベル、下半分＝メール2通）
- メール送信は自動的にメモリ内モック（`DemoMailSender`）になり、実際には送信されません。
  画面の送信結果には「テスト（実際には送信していません）」と表示されますが、
  送信履歴（MailHistory）には本番と同じく記録されるため履歴照会のデモは行えます
- Debugビルドでは `Demo:Enabled` の値にかかわらずモックが使われます（開発中の誤送信防止）

### ③ アプリケーションの発行

```
dotnet publish src\VisitorManagement.WinFormsApp -p:PublishProfile=SelfContained -c Release
dotnet publish src\VisitorManagement.WebReception -p:PublishProfile=SelfContained -c Release
```

受付Webは自己完結型・組み込みKestrelで起動するため、IIS や Azure App Service の設定は不要です。
実行ファイルをダブルクリックするだけで起動します。

## 4. デモシナリオ

### シナリオ1: 事前予約 → QR発行 → 入館 → 退館（中核機能）

1. 管理アプリを `demo-reception` でログイン
2. 「来館予約管理」→「新規登録」
3. 代表者1名と同行者を入力して保存
   - **QRコードは代表者1名にのみ発行される**点を強調（同行者は個別QRを持たない）
   - 保存後にQRコード表示画面が開くので「画像を保存」でPNGを取り出す
   - 「レイアウトをPDFで確認」で、ラベル（上半分）と実際に送信される
     メール2通の文面（下半分：左＝予約登録者控え／右＝来訪者代表宛）をA4 1枚で提示できる
4. 受付Webを起動し `demo-reception` でログイン
5. 受付画面でQRコードを読み取り（QRリーダー、または画像をスマートフォン等で表示して読取）
   - **1回目 → 入館**：グループ全員が「入館中」として大きく表示される
   - **2回目 → 退館**：グループ全員が「退館済」
   - **3回目 → エラー**：「このQRコードは既に退館処理済みです」

### シナリオ2: 当日受付（予約なし来館者）

1. 受付画面の「予約がない方はこちら（当日受付）」をクリック
2. **画面が日英併記**である点を提示（設計書 6.12節の多言語対応対象）
3. 会社名・お名前を入力（メールアドレスは任意）、同行者も同時に入力
4. 「登録してQRコードを発行」→ **登録した時点で入館登録まで完了**し、
   入館時刻・QRコード・ラベル印刷結果が表示される
   - 受付に来館者がいる状態で登録するため、登録＝入館として扱う点を説明
   - 発行するQRコードは**退館用**である点を強調（お帰りの際に読み取る）
5. 「ラベルレイアウトをPDFで確認」をクリック
   - **上半分**：A4用紙内にラベル実寸が点線枠で示され、QRコード・社名・ロゴが配置される
   - プリセット2・3が「未設定（導入時ヒアリングで個別設定）」と表示される点を説明
   - **下半分**：実際に送信される来館案内メールの文面が、左＝予約登録者（控え）宛／
     右＝来訪者代表（招待者）宛で並ぶ
   - 当日受付では控えメールを送信しない運用のため、左カラムには
     「当日受付では控えメールは送信されません（レイアウト見本）」の注記が付く
6. 発行されたQRを受付画面で読み取ると「退館」になることを確認する
   （事前予約のQRは 1回目＝入館 / 2回目＝退館、当日受付のQRは退館用）

### シナリオ3: 権限ロールによる制御（RBAC）

1. 管理アプリを `demo-general`（一般ロール）でログインし直す
2. メニューが「来館予約管理」「履歴照会」のみになる
3. 予約一覧を開くと**自分が登録した予約のみ**が表示される。
   登録・編集・キャンセルは行えるが、**削除とメール再送信のボタンは表示されない**
   （設計書 11.6節。一般ロールは自分が招く来館者の予約のみを自分で運用できる）
4. `demo-reception`（受付ロール）では履歴が**自身の所属拠点分のみ**になる
5. `demo-admin`（管理者）では全拠点・全件が見える

### シナリオ4: グループはぐれ対応（手動退館処理）

1. `demo-reception` で「手動退館処理」を開く
2. 入館中の来館者一覧から同行者1名を選択し「退館処理」
3. **選択した1名のみが退館済**になり、代表者は入館中のままである点を確認

### シナリオ5: 履歴照会とCSV出力

1. 「履歴照会」で入退館履歴・メール送信履歴をタブ切替
2. メール送信履歴に招待者宛・予約登録者宛が**別レコード**で記録されている点を提示
3. 「CSV出力」でExcelで開けるCSV（BOM付きUTF-8）を出力

### シナリオ6: DB切替アーキテクチャ（設計書の中核）

1. `demo-admin` で「システム設定確認」を開く
2. DB方式・リトライ方針・メール送信方式・ラベル印刷方式の現在値が表示される
3. **設定ファイルの1項目（`Database:Provider`）を変更して再起動するだけで
   SQL Server Express ⇔ Azure SQL Database を切り替えられる**点を説明
   （ビルドの出し分けは不要。同一バイナリで両対応）

## 5. デモ後のリセット

管理アプリを `demo-admin` でログインし、「システム」→「サンプルデータ初期化」を実行します。
デモ用DBの内容がすべて削除され、シード状態に戻ります（管理者ロール専用）。

## 6. デモ環境の制限事項（設計書 19.5節）

- メール送信・ラベル印刷は実際には行われません（画面表示またはPDFでの確認のみ）
- 事前に SQL Server Express のセットアップが必要です
- ノートPC1台でのスタンドアロン動作を想定しており、複数拠点・複数端末の負荷検証には使用しません
- Azure SQL Database 固有の挙動（PITR、Service Tier起因の性能特性）は確認できません
