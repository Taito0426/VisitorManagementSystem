 1. システム全体構成
====================================================================

【ソリューション構成】(VisitorManagement.slnx)

  VisitorManagement.slnx
   ├─ src\VisitorManagement.Core                        … エンティティ・契約・業務ルール（外部依存なし）
   ├─ src\VisitorManagement.Application                 … 業務ロジック（サービス層）
   ├─ src\VisitorManagement.Infrastructure.Data         … Dapper Repository（DB方式共通）
   ├─ src\VisitorManagement.Infrastructure.Data.SqlExpress … SQL Server Express 用の差分
   ├─ src\VisitorManagement.Infrastructure.Data.AzureSql   … Azure SQL Database 用の差分
   ├─ src\VisitorManagement.Infrastructure.Mail         … メール送信
   ├─ src\VisitorManagement.Infrastructure.Printing     … QRコード生成・ラベル印刷
   ├─ src\VisitorManagement.Composition                 … DI合成（Provider切替）
   ├─ src\VisitorManagement.WinFormsApp                 … 管理アプリ（実行exe）
   ├─ src\VisitorManagement.WebReception                … 受付Web/API（実行exe）
   ├─ src\VisitorManagement.BatchRunner                 … 定時バッチ（実行exe）
   └─ tests\VisitorManagement.Tests                     … 単体テスト（xUnit）

【プロジェクト参照関係（依存の向き）】

                          Core
                            ↑
        ┌───────────────────┼───────────────────┐
   Application    Infrastructure.Data    Infrastructure.Mail
        ↑                   ↑            Infrastructure.Printing
        │          ┌────────┴────────┐            ↑
        │      .SqlExpress        .AzureSql        │
        └───────────────┬───────────────┬──────────┘
                        Composition
                             ↑
        ┌────────────────────┼────────────────────┐
   WinFormsApp          WebReception          BatchRunner

  ・Core はどこにも依存しない（最も内側の層）。
  ・Application は Core のみ参照する（インフラを知らない）。
  ・Infrastructure.* は Core のインターフェースを実装する（依存性逆転）。
  ・Composition が全部を束ねてDIを組み立てる。
  ・3つの実行アプリはすべて Composition だけを参照し、
    同じ AddVisitorManagement(configuration) を呼ぶ。

このため、「新しい画面を作る」は主に実行アプリ側の作業、
「新しい業務ロジック・データ項目を作る」は
Core → Application → Infrastructure.Data の順に手を入れる作業になります。

【設計書のプロジェクト構成との差異】
  設計書4.3節は7プロジェクト構成ですが、実装では次の4つを追加しています。
    ・Application     … サービス層。設計書に配置先の定義がなく、WinFormsと
                         受付Webで同一ロジックを共有する必要があるため
    ・Infrastructure.Printing … ILabelPrinter（設計書19章で新設）の実装配置先
    ・Composition     … DI合成。Application をインフラ非依存に保つため
    ・BatchRunner     … タスクスケジューラから呼ぶ実行基盤

 3.1 管理アプリ（WinFormsApp\Program.cs）

    ① provider.InitializeDemoAsync()
         Demo:Enabled=true のときのみスキーマ作成＋シード投入

 3.3 DI登録の中身（Composition\ServiceCollectionExtensions.cs）
────────────────────────────────────────────────────

  public static IServiceCollection AddVisitorManagement(
      this IServiceCollection services, IConfiguration configuration)
  {
      DapperConfiguration.Configure();          // 型マッピング（DateOnly等）

      services.AddVisitorManagementSettings(configuration);  // Optionsバインド
      services.AddDatabaseProvider(configuration);           // ★DB方式の切替
      services.AddRepositories();
      services.AddMailProvider(configuration);               // ★メール方式の切替
      services.AddPrintingProvider(configuration);           // ★印刷方式の切替
      services.AddArchiveStorage(configuration);             // ★保管先の切替
      services.AddApplicationServices();
      return services;
  }

  ★DB方式の切替はここだけ（設計書4.4節そのまま）

  private static IServiceCollection AddDatabaseProvider(
      this IServiceCollection services, IConfiguration configuration)
  {
      var provider = configuration[$"{DatabaseSettings.SectionName}:Provider"];

      if (string.Equals(provider, DatabaseProviderNames.AzureSql,
                        StringComparison.OrdinalIgnoreCase))
      {
          services.AddSingleton<IDbConnectionFactory, AzureSqlConnectionFactory>();
          services.AddSingleton<IDbRetryPolicy, AzureSqlRetryPolicy>();
          services.AddSingleton<IBackupService, AzureSqlBackupService>();
      }
      else
      {
          services.AddSingleton<IDbConnectionFactory, SqlExpressConnectionFactory>();
          services.AddSingleton<IDbRetryPolicy, NoRetryPolicy>();
          services.AddSingleton<IBackupService, SqlExpressBackupService>();
      }

      services.AddSingleton<IDbSessionFactory, DbSessionFactory>();
      services.AddSingleton<IDatabaseInitializer, DatabaseInitializer>();
      return services;
  }

 5. データベース関連（スキーマ・Dapper・トランザクション）
====================================================================

────────────────────────────────────────────────────
 5.1 スキーマの管理
────────────────────────────────────────────────────
  ★本システムは Dapper（手書きSQL）であり、EF Core のマイグレーションは
    ありません。スキーマの正本は次のファイルです。

      db\01_CreateSchema.sql

  ・IF OBJECT_ID(...) IS NULL でテーブルを作る冪等スクリプトです。
  ・インデックスはテーブル作成とは別の冪等ブロックにしています。
    （既存DBへ再実行したとき、不足しているインデックスだけが追加されます）
  ・このファイルは Infrastructure.Data の .csproj から EmbeddedResource として
    リンク同梱され、デモ版のスキーマ自動作成に再利用されます（二重管理しない）。

      <EmbeddedResource Include="..\..\db\01_CreateSchema.sql"
                        LogicalName="VisitorManagement.Infrastructure.Data.Sql.CreateSchema.sql" />

  ・既存DBに列を追加する場合は ALTER 文を別ファイル（例 db\03_AlterXxx.sql）で
    用意し、01_CreateSchema.sql にも同じ定義を反映してください。

────────────────────────────────────────────────────
 5.2 ★QUOTED_IDENTIFIER の注意（必ず読むこと）
────────────────────────────────────────────────────
  dbo.Visitors にはフィルター選択インデックスがあります。

      CREATE UNIQUE NONCLUSTERED INDEX UQ_Visitors_GroupRepresentative
          ON dbo.Visitors (ReservationGroupId) WHERE IsRepresentative = 1;

  （1予約グループに代表者は1名だけ、をDB側でも保証するため）

  SQL Server の仕様上、フィルター選択インデックスを持つテーブルへの
  INSERT / UPDATE / DELETE は QUOTED_IDENTIFIER が ON でなければ
  エラー 1934 で失敗します。

    ・アプリ  : Microsoft.Data.SqlClient は既定 ON のため対応不要
    ・sqlcmd  : 既定 OFF。★-I オプションを必ず付ける
    ・スクリプト: 冒頭で SET QUOTED_IDENTIFIER ON; を実行する

────────────────────────────────────────────────────
 5.3 Dapper の型マッピング
────────────────────────────────────────────────────
  Infrastructure.Data\DapperConfiguration.cs で3つのハンドラを登録しています。
  起動時に DapperConfiguration.Configure() が1回だけ呼ばれます
  （AddVisitorManagement の先頭）。

    DateOnlyTypeHandler     date 列 ↔ DateOnly（Visitors.VisitDate）
    TimeOnlyTypeHandler     time 列 ↔ TimeOnly（VisitTimeFrom / VisitTimeTo）
    UtcDateTimeTypeHandler  datetime2 の UTC 往復を保証

  ★日時はすべて UTC で保存します。
    SQL Server の datetime2 は種別（Kind）を保持しないため、
    UtcDateTimeTypeHandler が読取時に DateTimeKind.Utc を明示します。
    画面表示は HistoryService.ToLocalText(...) でローカル時刻へ変換します。

────────────────────────────────────────────────────
 5.4 Repository の書き方
────────────────────────────────────────────────────
  すべての Repository は RepositoryBase を継承します。

  public sealed class CompanyRepository(
      IDbSessionFactory sessionFactory, IDbRetryPolicy retryPolicy)
      : RepositoryBase(sessionFactory, retryPolicy), ICompanyRepository
  {
      private const string SelectColumns = """
          SELECT  CompanyId, CompanyName, Address, Tel
          FROM    dbo.Companies
          """;

      public Task<Company?> GetByIdAsync(int companyId, IDbSession? session = null)
          => ExecuteAsync(session, s => s.Connection.QuerySingleOrDefaultAsync<Company>(
              new CommandDefinition($"{SelectColumns} WHERE CompanyId = @CompanyId;",
                  new { CompanyId = companyId }, s.Transaction)));
  }

  ■ RepositoryBase.ExecuteAsync の役割
    ・session が null      → 自前でセッションを作り、リトライ方針を適用する
    ・session が渡された   → 呼び出し側のトランザクション内なので
                             ★リトライを適用せずそのまま実行する
                             （途中でリトライすると整合性を壊すため）

  ■ 動的な検索条件（SearchAsync）の書き方
    StringBuilder で WHERE を組み立て、DynamicParameters に全パラメータを
    無条件で追加します（未使用でもエラーになりません）。

      var sql = new StringBuilder(SelectColumns.Replace("SELECT  ", $"SELECT  {top}"));
      sql.AppendLine().Append("WHERE 1 = 1");
      if (!string.IsNullOrWhiteSpace(condition.VisitorName))
          sql.AppendLine().Append("  AND v.VisitorName LIKE @VisitorNamePattern");
      …
      parameters.Add("VisitorNamePattern", $"%{EscapeLike(condition.VisitorName)}%");

    ★LIKE検索は必ず VisitorRepository.EscapeLike でワイルドカードを
      エスケープしてください（% _ [ をそのまま渡さない）。
    ★TOP は SELECT TOP (@Max) にせず、C#側で文字列に埋め込みます
      （@Max が NULL のとき SQL エラーになるため）。

────────────────────────────────────────────────────
 5.5 トランザクションの書き方
────────────────────────────────────────────────────
  複数テーブルにまたがる更新は、サービス層で IDbSession を作って
  各 Repository に渡します。

      using (var session = sessionFactory.CreateSession(beginTransaction: true))
      {
          await visitorRepository.CreateAsync(representative, session);
          foreach (var companion in companions)
              await visitorRepository.CreateAsync(companion, session);

          await qrTokenRepository.CreateAsync(token, session);
          session.Commit();
      }

  ・Commit を呼ばずに using を抜けると自動的にロールバックされます。
  ・トランザクション境界は必ずサービス層に置きます（Repositoryに置かない）。

 6. 共通の型・命名規則
====================================================================

────────────────────────────────────────────────────
 6.1 命名規則
────────────────────────────────────────────────────
  ・クラス／メソッド／プロパティ : PascalCase
  ・ローカル変数／引数           : camelCase
  ・privateフィールド            : _camelCase
  ・インターフェース             : I + 名詞（IVisitorRepository）
  ・非同期メソッド               : 末尾 Async
  ・テーブル名                   : マスタは複数形（Sites/Operators/Companies）
                                   トランザクションも複数形（Visitors/AccessLogs）
  ・列名                         : PascalCase（エンティティのプロパティ名と一致）
  ・インデックス                 : IX_テーブル_列 ／ 一意は UQ_テーブル_列
  ・コメント                     : ★日本語。処理の意図（なぜ）を書く
  ・インデント                   : スペース4つ（C#）／スペース2つ（JSON・JS）

────────────────────────────────────────────────────
 6.2 例外の使い分け
────────────────────────────────────────────────────
  BusinessRuleException      業務ルール違反（入力不備・状態不整合）。
                             メッセージをそのままユーザーへ表示してよい。
                               throw new BusinessRuleException("代表者の氏名を入力してください。");

  PermissionDeniedException  権限不足。
                               throw PermissionDeniedException.ForOperation("手動退館処理");

  それ以外の例外              技術的な失敗。ユーザーには詳細を見せず、
                             UiTheme.ShowError / Error ページで丸めて表示する。

  ★UiTheme.ShowError は例外の種別で文言を切り替えます。
      BusinessRuleException / PermissionDeniedException → メッセージをそのまま表示
      SqlException → 「一時的にデータベースに接続できません。…」
      その他       → 「処理中にエラーが発生しました。」＋例外メッセージ

────────────────────────────────────────────────────
 6.3 覚えておくと便利な共通処理
────────────────────────────────────────────────────
  VisitRules.CalculateExpiresAtUtc(date, time)  QR有効期限（+2時間）
  VisitRules.CalculateValidFromUtc(date, time)  QR有効開始（-30分）
  VisitRules.CanCancel(status)                  キャンセル可否
  VisitRules.CanResendMail(status, type)        メール再送信可否
  PermissionPolicy.CanXxx(ctx)                  権限判定
  PermissionPolicy.ApplyViewScope(ctx, cond)    閲覧範囲を検索条件へ反映
  HistoryService.ToText(...)                    ステータス等の日本語表示名
  HistoryService.ToLocalText(utc)               UTC → ローカル時刻表示
  HistoryService.Escape(value)                  CSVフィールドのエスケープ
  UiTheme.CreateGrid() / TextColumn(...)        一覧グリッドの生成
  UiTheme.RunWithWaitCursorAsync(form, action)  処理中カーソル

 7. 実例で学ぶ：来館予約（Reservation）の全体フロー
====================================================================

「予約を登録すると、QRコードが発行され、メールが送信される」までを
どのファイルがどう連携しているかを追いかけます。

────────────────────────────────────────────────────
 ① 画面：WinFormsApp\Forms\ReservationEditForm.cs
────────────────────────────────────────────────────
  入力値を ReservationInput（DTO）に詰めてサービスを呼ぶだけ。
  業務判断はここに書きません。

      var input = new ReservationInput
      {
          SiteId = siteId.Value,
          VisitDate = DateOnly.FromDateTime(_visitDatePicker.Value),
          VisitTimeFrom = TimeOnly.FromDateTime(_timeFromPicker.Value),
          …
          Representative = new ReservationMemberInput { … },
          Companions = [.. _companions.Where(c => !string.IsNullOrWhiteSpace(c.VisitorName))
                                      .Select(c => new ReservationMemberInput { … })],
      };

      result = await _reservationService.CreateAsync(input, _ctx);

────────────────────────────────────────────────────
 ② DTO：Core\Dtos\ReservationInput.cs
────────────────────────────────────────────────────
  代表者1名＋同行者リストという構造をそのまま表現します。
  ★事前予約と当日受付で同じDTOを使います（設計書6.6節「特別な例外フローを
    設けない」を素直に実装したもの）。

 ③ サービス：Application\Services\ReservationService.CreateAsync
────────────────────────────────────────────────────

    1) 権限チェック

             throw PermissionDeniedException.ForOperation("来館予約の登録");
         ※編集・キャンセルでは、これに加えて対象予約の代表者行に対して

    7) メール送信（★当日受付は予約登録者宛の控えを省略）
         var sendToRegistrant = input.ReservationType == ReservationType.Advance;
         await mailDeliveryService.SendInvitationAsync(
             group, registeredBy, qrCodePng, MailType.VisitInvitation, sendToRegistrant);

  ★メール送信は「トランザクションの外」で行います。
    送信に時間がかかってもDBのロックを保持しないためです。

────────────────────────────────────────────────────
 ④ メール：Application\Services\MailDeliveryService.cs
────────────────────────────────────────────────────
  宛先ごとに送信し、成功・失敗のどちらでも MailHistory に1件記録します。

      catch (Exception ex) when (ex is InvalidOperationException or IOException or TimeoutException)
      {
          // 送信失敗は予約登録の成否に影響させず、履歴に失敗として残す
          await RecordAsync(representative.VisitorId, mailType, recipientType, ex.Message);
          return new MailDeliveryResult(recipientType, address, false, ex.Message);
      }

  ★catch は種別を限定しています。想定外の例外まで握り潰さないためです。

 ⑤ Repository：Infrastructure.Data\Repositories\VisitorRepository.cs
────────────────────────────────────────────────────
  SQLを書くのはここだけ。DB方式による分岐は一切ありません。

────────────────────────────────────────────────────
 ⑥ 読み取り側：Application\Services\AccessService.ScanAsync
────────────────────────────────────────────────────
  同じデータを受付Webから使う側の流れです。

    1) トークン取得（GetByTokenValueAsync）
    2) グループ取得（GetByGroupIdAsync）
    3) 検証：IsValid → キャンセル → UsedCount>=2 → 期限切れ → 受付時間前
         いずれもエラー時は代表者行に AccessLogs を1件記録して終了
    4) ★TryConsumeAsync で排他的に読取回数を加算

    6) グループ内の来館者ごとに AccessLogs を1件ずつ記録

 11. 権限（RBAC）の実装ルール
====================================================================

  権限判定は必ず Core\Security\PermissionPolicy.cs の判定メソッドを使います。
  各画面・各サービスで if (role == ...) と書かないでください。

  ■ 判定メソッド（設計書11.6節の権限マトリクスと1対1）
      CanCreateReservation    来館予約の登録（全ロール）
      CanEditReservation      来館予約の編集・キャンセル（全ロール）
      CanDeleteReservation    来館予約の削除（管理者・受付のみ）
      CanOperateOnReservation 対象の予約を操作できるか（一般は自分の登録分のみ）
                              ★一般ロールに編集・キャンセルを許可したため、
                                ロール判定に加えて必ずこの行単位判定も併用すること。
      CanUseReception         当日受付登録・入退館受付
      CanManualCheckOut       手動退館処理
      CanResendMail           メール再送信
      CanManageCompanies      会社名マスタ管理
      CanManageSites          拠点マスタ管理
      CanManageOperators      操作ユーザー管理
      CanViewSystemSettings   システム設定確認
      CanResetDemoData        サンプルデータ初期化

  ■ 閲覧範囲（履歴・予約）
      ResolveViewScope(ctx, requestedSiteId) → (SiteId, CreatedByOperatorId)
        管理者 : (画面で選択した拠点, null)      … 全拠点・全件
        受付   : (自分の所属拠点, null)          … 他拠点は選べない
        一般   : (画面で選択した拠点, 自分のId)  … 自分が登録した予約のみ

      検索条件へは ApplyViewScope で反映します。

          PermissionPolicy.ApplyViewScope(ctx, condition);
          return visitorRepository.SearchAsync(condition);

  ■ 実装の3層構造（★UIだけに頼らない）
      1) 画面    メニュー・ボタンを非表示／非活性にする
      2) サービス PermissionDeniedException を投げる
      3) API     403 を返す（受付Webの /api/access/scan 等）

    実際、一般ロールで /api/access/scan を直接呼ぶと 403 が返ることを
    検証済みです（docs\動作検証確認項目.txt 14章）。

  ■ 新しい権限を足したいとき
      ① PermissionPolicy に CanXxx メソッドを追加
      ② サービス層で判定して PermissionDeniedException を投げる
      ③ 画面の ApplyPermissions に反映
      ④ tests\PermissionPolicyTests.cs にロール3種分のテストを追加

 15. よくある間違い・注意点チェックリスト
====================================================================

【DB・SQL】
  □ ★sqlcmd に -I を付けたか
     → 付けないと Visitors への DDL/DML がエラー1934で失敗する
  □ INSERT/UPDATE に列を足したとき、パラメータの匿名オブジェクトにも追加したか
     → 漏れると「スカラー変数 "@Xxx" を宣言してください」エラー
  □ 日時を UTC で保存しているか（DateTime.UtcNow）
     → 表示時に HistoryService.ToLocalText でローカルへ変換する
  □ LIKE検索で EscapeLike を通したか
  □ トランザクションの境界をサービス層に置いたか
  □ 複数テーブル更新で session を全 Repository に渡したか
     → 渡し忘れると別接続になり、同一トランザクションにならない

【業務ルール】
  □ ★QRトークンを代表者以外に発行していないか
  □ ★同行者の VisitorEmail に値を入れていないか（必ず null）
  □ グループ一括更新でキャンセル済みを除外しているか
  □ 読取回数の更新に TryConsumeAsync を使ったか（同時読取の排他）
  □ 有効期限の計算を VisitRules 経由にしたか（独自計算しない）

【権限】
  □ サービス層でも権限判定したか（UIで隠すだけにしていないか）
  □ APIでも権限判定したか（403を返す）
  □ 検索に ApplyViewScope を通したか（一般ロールに他人の予約が見えないか）

【WinForms】
  □ async void のイベントハンドラで try/catch したか
     → 例外を投げるとアプリが落ちる
  □ フォームのコンストラクタ引数を IServiceProvider 1つにそろえたか
     → ShowDialog<TForm>() が Activator.CreateInstance で生成するため
  □ 権限のない画面を直接開いていないか
     → LoadAsync 内で PermissionDeniedException → MessageBox となり
       画面外での自動テストがハングする
  □ System.Windows.Forms.Application を明示したか
     → VisitorManagement.Application 名前空間と衝突する

【受付Web】
  □ PageModel に [Authorize] を付けたか
  □ JSON POST で antiforgery を明示的に検証したか
  □ ★Razor は日本語を数値文字参照（&#x53D7; 等）で出力する
     → HTMLの文字列比較で日本語を判定しない（自動テスト時の落とし穴）

【メール・印刷】
  □ 送信失敗で業務処理を止めていないか（履歴に記録して続行する）
  □ QRコードを24bit PNGで生成しているか
     → 1bitグレースケールPNGは PDFsharp が読めない（Unsupported image format）
  □ ラベル印刷の失敗で当日受付の登録を失敗させていないか

【設定・運用】
  □ appsettings.Local.json を .gitignore 対象のままにしているか
  □ 接続文字列のパスワードを平文でコミットしていないか
  □ ★BACKUP DATABASE に COMPRESSION を付けていないか
     → Express Edition では未サポート（エラー1844）。
       エディションを判定して INIT, CHECKSUM に落とす

【PowerShell（開発作業時）】
  □ ★Get-Content -Raw → Set-Content の往復で日本語ファイルを壊していないか
     → PowerShell 5.1 は BOM なし UTF-8 を ANSI として読むため文字化けする。
       ソース編集はエディタで行うこと
  □ 日本語コメントを含む .ps1 に BOM を付けたか
     → BOM なしだと PowerShell 5.1 が文字化けする
